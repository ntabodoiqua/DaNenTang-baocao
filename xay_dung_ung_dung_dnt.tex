\section{Xây dựng ứng dụng đa nền tảng}
\subsection{Kiến trúc ứng dụng}

\subsubsection{Lựa chọn kiến trúc phần mềm và giải thích sơ bộ}

Ứng dụng \textbf{``Đi chợ tiện lợi''} được xây dựng theo mô hình \textbf{Client-Server Architecture} kết hợp với \textbf{RESTful API}, trong đó:

\begin{itemize}
    \item \textbf{Client (Frontend):} Ứng dụng di động đa nền tảng phát triển bằng React Native + Expo.
    \item \textbf{Server (Backend):} Hệ thống API server xây dựng bằng Spring Boot (Java).
    \item \textbf{Database:} PostgreSQL để lưu trữ dữ liệu.
\end{itemize}

\paragraph{Kiến trúc Backend: Clean Architecture} ~\\
Phía Backend được thiết kế theo \textbf{Clean Architecture} với nguyên tắc \textbf{Dependency Inversion} - các lớp bên trong không phụ thuộc vào các lớp bên ngoài. 
\begin{figure}[H]
    \centering
    \includegraphics[width=0.75\textwidth]{bieu_do/PackageDiagram.png}
    \caption{Sơ đồ phân lớp các gói (Package Diagram) theo Clean Architecture}
\end{figure}

\paragraph{Vai trò của gói domain (Tầng lõi)} ~\\
Đây là thành phần quan trọng nhất, chứa các thực thể nghiệp vụ (Entities) và các giao diện kho lưu trữ (Repository Interfaces). Gói này tập trung các quy tắc nghiệp vụ cốt lõi, được thiết kế độc lập hoàn toàn với framework hay công cụ bên thứ ba, giúp lõi ứng dụng ổn định trước các thay đổi công nghệ.

\paragraph{Vai trò của gói application (Tầng nghiệp vụ)} ~\\
Gói này chứa các kịch bản sử dụng (Use Cases) điều phối logic ứng dụng. Nó đóng vai trò cầu nối, tiếp nhận yêu cầu từ tầng Presentation để thực thi các chức năng nghiệp vụ cụ thể thông qua việc tương tác với các Entity và Interface tại tầng Domain.

\paragraph{Vai trò của gói presentation (Tầng giao tiếp)} ~\\
Đảm nhận nhiệm vụ xử lý tương tác với người dùng qua các API Controller. Các thành phần tại đây tiếp nhận Request HTTP, giải mã dữ liệu, chuyển giao cho tầng Application xử lý và trả về Response phù hợp cho ứng dụng Client.

\paragraph{Vai trò của gói infrastructure (Tầng hạ tầng)} ~\\
Chứa các cài đặt kỹ thuật chi tiết hỗ trợ hệ thống, bao gồm triển khai thực tế các Repository (JPA), cấu hình cơ sở dữ liệu PostgreSQL, thiết lập bảo mật (Security) và các bộ chuyển đổi dữ liệu (Mappers).

\paragraph{Quy tắc thiết kế và sự phụ thuộc} ~\\
Hệ thống tuân thủ nghiêm ngặt nguyên tắc phụ thuộc một chiều hướng vào tầng \textit{domain}. Các gói được phân tầng rõ ràng: tầng \textit{presentation} không được phép truy cập trực tiếp \textit{domain} mà phải thông qua \textit{application}. Đồng thời, việc áp dụng Dependency Inversion giúp tầng lõi không biết về sự tồn tại của các Framework bên ngoài, đảm bảo tính độc lập và khả năng kiểm thử (Testable) tối đa.

\paragraph{Kiến trúc Frontend: Component-Based Architecture} ~\\
Phía Frontend sử dụng \textbf{Component-Based Architecture} kết hợp với \textbf{React Query} cho server state và \textbf{Zustand} cho client state:
\begin{itemize}
    \item \textbf{Component-Based:} Giao diện được chia thành các component độc lập, tái sử dụng.
    \item \textbf{Unidirectional Data Flow:} Luồng dữ liệu một chiều với State Management.
\end{itemize}

\subsubsection{Các cải tiến so với lý thuyết}

\begin{enumerate}
    \item \textbf{Tách biệt JPA Entity và Domain Entity:} Domain Entity là pure Java object, JPA Model chứa các annotations. Mapper class chịu trách nhiệm chuyển đổi qua lại, giúp lõi nghiệp vụ hoàn toàn sạch (clean).
    \item \textbf{Use Case Pattern:} Thay vì một Service class khổng lồ, mỗi UseCase tập trung vào một nhóm chức năng cụ thể, giúp tuân thủ nguyên tắc Single Responsibility.
    \item \textbf{Repository Pattern với Interface Segregation:} Domain layer định nghĩa interface, Infrastructure layer triển khai thực tế. Điều này cho phép dễ dàng thay đổi công nghệ lưu trữ (ví dụ từ SQL sang NoSQL) mà không sửa đổi logic nghiệp vụ.
    \item \textbf{React Query cho Server State:} Thay vì quản lý mọi thứ trong Global State (như Redux), ứng dụng dùng React Query để tối ưu hóa việc caching, đồng bộ dữ liệu và giảm thiểu số lượng API call không cần thiết.
\end{enumerate}

\subsection{Tổ chức thư mục của dự án}
Cấu trúc tệp và thư mục của một dự án đóng vai trò quyết định đến mức độ dễ dàng trong việc điều hướng, bảo trì và mở rộng hệ thống. Một tổ chức thư mục hợp lý giúp các nhà phát triển nhanh chóng tìm thấy các thành phần nghiệp vụ hoặc kỹ thuật tương ứng mà không làm xáo trộn các lớp kiến trúc.

\subsubsection{Cấu trúc mã nguồn Backend (Spring Boot)}

Dựa trên mô hình Clean Architecture, mã nguồn Backend được tổ chức phân lớp nghiêm ngặt để tách biệt logic nghiệp vụ khỏi các chi tiết hạ tầng.

\begin{verbatim}
src/main/java/hust/project/freshfridge/
|-- FreshfridgeApplication.java   # Diem khoi chay ung dung
|-- domain/                       # LAYER 1: Nghiep vu cot loi
|   |-- constant/                 # Hang so nghiep vu
|   |-- entity/                   # Domain Entities (Pure Java Objects)
|   |-- exception/                # Ngoai le cap nghiep vu
|   |-- repository/               # Repository Interfaces (Ports)
|   |-- service/                  # Domain Services
|-- application/                  # LAYER 2: Logic ung dung
|   |-- dto/                      # Data Transfer Objects (Request/Response)
|   |-- scheduler/                # Cac tac vu lap lich tu dong
|   |-- usecase/                  # Use Cases / Application Services
|-- infrastructure/               # LAYER 3: Cac thanh phan ben ngoai
|   |-- config/                   # Cau hinh Spring Boot
|   |-- persistence/              # Cai dat luu tru (JPA, Models, Mappers)
|   |-- security/                 # Cau hinh bao mat (JWT, Auth)
|   |-- service/                  # Dich vu ha tang ky thuat
|-- presentation/                 # LAYER 4: Tang giao tiep (API)
|   |-- controller/               # REST Controllers
|   |-- exception/                # Global Exception Handlers

src/main/resources/
|-- application.yaml              # Cau hinh tham so moi truong
|-- db/migration/                 # Quan ly phien ban DB (Flyway)
\end{verbatim}

\paragraph{Phân tích ưu và nhược điểm (Backend)}
\begin{itemize}
    \item \textbf{Ưu điểm:} Tách biệt trách nhiệm rõ ràng (Separation of Concerns), giúp bảo trì dễ dàng khi cần thay đổi cơ sở dữ liệu hoặc framework mà không ảnh hưởng đến lõi nghiệp vụ. Cấu trúc này cũng tối ưu cho việc viết Unit Test cho tầng \textit{domain}.
    \item \textbf{Nhược điểm:} Độ phức tạp ban đầu cao và phát sinh nhiều mã nguồn bổ trợ (Boilerplate code) như các Mapper và DTO để chuyển đổi dữ liệu giữa các lớp.
\end{itemize}

\subsubsection{Cấu trúc mã nguồn Frontend (React Native)}

Mã nguồn Frontend được tổ chức theo hướng mô-đun hóa và quản lý theo tính năng (feature-based), giúp tối ưu hóa việc tái sử dụng thành phần giao diện.

\begin{verbatim}
frontend/
|-- App.tsx                 # Diem khoi dau (Root Component)
|-- app.json                # Cau hinh Expo/React Native
|-- src/                    # Ma nguon chinh
|   |-- api/                # Tang giao tiep mang (Axios client, Endpoints)
|   |-- components/         # UI Components tai su dung (Common, Form)
|   |-- constants/          # Hang so toan cuc
|   |-- hooks/              # Custom React Hooks
|   |-- screens/            # Cac man hinh theo tinh nang (Auth, Food, Home...)
|   |-- services/           # Business logic services (Auth, Storage)
|   |-- store/              # Quan ly trang thai (Zustand/Redux)
|   |-- theme/              # Design system (Colors, Typography)
|   |-- types/              # TypeScript definitions
|   |-- utils/              # Ham tien ich dung chung
|   |-- validation/         # Quy tac kiem tra du lieu (Zod/Yup)
\end{verbatim}

\paragraph{Phân tích ưu và nhược điểm (Frontend)}
\begin{itemize}
    \item \textbf{Ưu điểm:} Cách tổ chức theo \textit{screens} và \textit{components} giúp nhà phát triển dễ dàng định vị mã nguồn theo chức năng hiển thị. Việc tách riêng tầng \textit{api} và \textit{store} giúp quản lý luồng dữ liệu tập trung, tránh tình trạng logic nghiệp vụ bị trộn lẫn vào giao diện.
    \item \textbf{Nhược điểm:} Cấu trúc thư mục có phân cấp sâu, đòi hỏi việc thiết lập Path Aliases (đường dẫn tắt) trong cấu hình TypeScript để tránh các đường dẫn import quá dài gây khó đọc.
\end{itemize}

\paragraph{Mô tả các mối quan hệ nghiệp vụ}
\begin{itemize}
    \item \textbf{Điều phối nghiệp vụ:} \texttt{ShoppingController} liên kết với \texttt{ShoppingUseCase} thông qua quan hệ \textit{Association} để xử lý các yêu cầu tạo, cập nhật và xóa danh sách mua sắm từ người dùng.
    \item \textbf{Nghịch đảo phụ thuộc (DIP):} Tầng nghiệp vụ (\texttt{ShoppingUseCase}) tương tác với dữ liệu thông qua giao diện \texttt{IShoppingListRepository}. Việc thực thi chi tiết tại lớp \texttt{ShoppingListRepositoryImpl} thuộc tầng Infrastructure giúp hệ thống dễ dàng bảo trì và thay đổi công nghệ lưu trữ mà không làm ảnh hưởng đến logic lõi.
    \item \textbf{Quản lý mặt hàng:} Mối quan hệ \textit{Composition} giữa \texttt{ShoppingList} và \texttt{ShoppingListItem} khẳng định tính toàn vẹn của dữ liệu; các mặt hàng mua sắm là thành phần không thể tách rời của một danh sách cụ thể.
    \item \textbf{Phân quyền và giao việc:} Quan hệ \textit{Association} từ \texttt{ShoppingList} tới thực thể \texttt{User} mô tả chức năng gán trách nhiệm đi chợ cho một thành viên cụ thể trong nhóm, đáp ứng yêu cầu theo dõi tiến độ mua sắm của ca sử dụng.
\end{itemize}

    \item \textbf{Điều phối nghiệp vụ:} \texttt{MealPlanUseCase} đóng vai trò trung tâm, điều phối logic kiểm tra quyền truy cập công thức và tính hợp lệ của thời gian bữa ăn. Nó phụ thuộc (\textit{Dependency}) vào các interface repository để tương tác với dữ liệu.

Mối quan hệ giữa \texttt{MealPlan} và \texttt{Recipe} đảm bảo mỗi kế hoạch bữa ăn luôn gắn liền với một hướng dẫn nấu ăn cụ thể.
    \item \textbf{Tính linh hoạt của hạ tầng:} Bằng việc sử dụng quan hệ \textit{Realization} giữa \\ \texttt{MealPlanRepositoryImpl} và \texttt{IMealPlanRepository}, hệ thống tách biệt hoàn toàn logic lưu trữ khỏi logic nghiệp vụ, cho phép thay đổi phương thức lưu trữ mà không ảnh hưởng đến các ca sử dụng của người dùng.
\end{itemize}

\end{itemize}

\paragraph{Giải thích thiết kế và quan hệ giữa các lớp}

    \item \textbf{Tầng Presentation và Application:} \texttt{GroupController} đóng vai trò là điểm tiếp nhận các yêu cầu như tạo nhóm (\textit{createGroup}), thêm thành viên (\textit{addMember}) hoặc rời nhóm (\textit{leaveGroup}), sau đó ủy thác cho \texttt{GroupUseCase} thông qua quan hệ \textit{Association}.
    \item \textbf{Logic nghiệp vụ tập trung:} \texttt{GroupUseCase} điều phối toàn bộ luồng nghiệp vụ của nhóm. Lớp này sử dụng quan hệ \textit{Dependency} tới các giao diện repository như \texttt{IGroupRepository} và \texttt{IGroupMemberRepository} để đảm bảo tính độc lập của tầng Domain theo kiến trúc Clean Architecture.
    \item \textbf{Cấu trúc ràng buộc thành viên:} Mối quan hệ \textit{Composition} từ \texttt{Group} tới \texttt{GroupMember} thể hiện rằng danh sách thành viên là một phần hữu cơ của nhóm; khi nhóm bị giải tán bởi quản trị viên, các bản ghi thành viên liên quan sẽ tự động bị xóa bỏ để bảo đảm tính toàn vẹn dữ liệu.
    \item \textbf{Tương tác hệ thống:} \texttt{GroupUseCase} kết hợp với \texttt{NotificationUseCase} (quan hệ \textit{Association}) để tự động gửi thông báo thời gian thực khi có biến động về nhân sự trong nhóm, ví dụ như gửi lời mời (\textit{GROUP\_INVITE}) hoặc thông báo thành viên mới gia nhập.
    \item \textbf{Thực thi hạ tầng:} Các lớp \texttt{Impl} tại tầng Infrastructure chịu trách nhiệm hiện thực hóa các giao diện trừu tượng (\textit{Realization}), kết nối logic ứng dụng với hệ quản trị cơ sở dữ liệu mà không làm lộ các chi tiết cài đặt kỹ thuật lên tầng nghiệp vụ.
\end{itemize}

\paragraph{Giải thích thiết kế và quan hệ giữa các lớp}
\begin{itemize}
    \item \textbf{Trung tâm điều phối dữ liệu:} \texttt{ReportController} liên kết với \texttt{ReportUseCase} qua quan hệ \textit{Association}. Tầng này chịu trách nhiệm cung cấp các điểm cuối (endpoints) để người dùng truy xuất các loại báo cáo khác nhau như báo cáo tổng quan (\textit{Overview}), báo cáo kho bếp (\textit{Kitchen}) và báo cáo mua sắm (\textit{Shopping}).
    \item \textbf{Phụ thuộc đa nguồn:} \texttt{ReportUseCase} thể hiện quan hệ \textit{Dependency} tới hàng loạt các giao diện kho lưu trữ (\texttt{IKitchenItemRepository}, \texttt{IShoppingListRepository}, v.v.). Điều này cho thấy tính chất của module báo cáo là tầng xử lý dữ liệu cấp cao, tổng hợp thông tin từ tất cả các mảng nghiệp vụ trong hệ thống.
    \item \textbf{Xử lý nghiệp vụ thống kê:} Tầng nghiệp vụ sử dụng các đối tượng dữ liệu như \texttt{KitchenItem} và \texttt{ShoppingList} để phân tích các chỉ số về hiệu quả đi chợ và mức độ lãng phí thực phẩm.
    \item \textbf{Tính đóng gói và bảo trì:} Việc tương tác hoàn toàn qua các interface giúp \texttt{ReportUseCase} không bị ảnh hưởng bởi cấu trúc bảng trong cơ sở dữ liệu. Quan hệ \textit{Realization} từ tầng Infrastructure đảm bảo rằng logic thống kê luôn được tách biệt khỏi các truy vấn SQL phức tạp phía dưới.
\end{itemize}

\begin{figure}[H]
    \centering
    \includegraphics[width=0.9\textwidth]{bieu_do/Package-UC8.png}
    \caption{Biểu đồ gói chi tiết cho UC8: Quản trị người dùng}
\end{figure}

\paragraph{Giải thích thiết kế và quan hệ giữa các lớp}
\begin{itemize}
    \item \textbf{Điều phối quản trị:} \texttt{AdminUserController} tại tầng Presentation tiếp nhận các yêu cầu đặc quyền từ Quản trị viên, liên kết với \texttt{AdminUserUseCase} qua quan hệ \textit{Association}. Tầng này được bảo vệ nghiêm ngặt bởi cơ chế phân quyền (\textit{Role-based Access Control}).
    \item \textbf{Logic nghiệp vụ và Xử lý ràng buộc:} \texttt{AdminUserUseCase} chịu trách nhiệm thực hiện các quy tắc như ngăn cấm Admin tự vô hiệu hóa tài khoản chính mình. Lớp này sử dụng quan hệ \textit{Dependency} tới \texttt{IUserRepository} để truy vấn và \texttt{IGroupRepository} để xử lý dọn dẹp dữ liệu nhóm (xóa nhóm nếu người dùng bị xóa là chủ nhóm).
    \item \textbf{Thực thể và Phân quyền:} Thực thể \texttt{User} đóng vai trò trung tâm lưu trữ trạng thái tài khoản. Quan hệ phụ thuộc tới Enum \texttt{Role} cho phép quản trị viên thay đổi vai trò giữa người dùng thông thường và quản trị viên một cách an toàn.
    \item \textbf{Thống kê và Báo cáo:} Bên trong \texttt{AdminUserUseCase} định nghĩa cấu trúc nội \texttt{UserStatistics} để tổng hợp các chỉ số về số lượng tài khoản đang hoạt động, đã xác thực hoặc đang bị khóa, hỗ trợ Admin trong việc nắm bắt sức khỏe hệ thống.
    \item \textbf{Tách biệt hạ tầng:} Việc hiện thực hóa giao diện qua \texttt{UserRepositoryImpl} (quan hệ \textit{Realization}) giúp logic quản trị người dùng không bị phụ thuộc vào các chi tiết kỹ thuật của PostgreSQL hay Spring Data JPA.
\end{itemize}

\subsection{Các giải pháp khác đã xây dựng trong chương trình}
Trong quá trình phát triển ứng dụng, bên cạnh các tính năng cốt lõi, nhóm đã triển khai một loạt các giải pháp kỹ thuật bổ trợ nhằm tối ưu hóa hiệu suất, tăng cường tính bảo mật và nâng cao trải nghiệm người dùng. Phần này trình bày chi tiết về cách thức xử lý giao tiếp hệ thống, quản lý dữ liệu và tận dụng các dịch vụ nền tảng của thiết bị di động.

\subsubsection{Cơ chế giao tiếp với Back-end và xử lý truy vấn API}

Trong môi trường ứng dụng di động, việc quản lý các luồng dữ liệu thông qua HTTP Request đòi hỏi sự tập trung để xử lý các vấn đề về xác thực và đồng bộ hóa. Hệ thống đã triển khai giải pháp dựa trên Axios và React Query:

\begin{itemize}
    \item \textbf{Axios Interceptors:} Thiết lập một instance Axios tập trung để quản lý logic giao tiếp. 
    \begin{itemize}
        \item \textit{Request Interceptor:} Tự động trích xuất JWT Token từ kho lưu trữ bảo mật và đính kèm vào header \texttt{Authorization} cho mọi yêu cầu.
        \item \textit{Response Interceptor:} Xử lý lỗi hệ thống tập trung. Đặc biệt, cơ chế tự động làm mới mã xác thực (Auto-refresh Token) được kích hoạt khi nhận mã lỗi 401, giúp duy trì phiên làm việc của người dùng mà không cần đăng nhập lại.
    \end{itemize}
    \item \textbf{Quản lý trạng thái Server với React Query:} Thay vì quản lý dữ liệu API bằng các biến state thông thường, dự án sử dụng \texttt{@tanstack/react-query} để tối ưu hóa hiệu suất thông qua:
    \begin{itemize}
        \item Cơ chế \textit{Caching} dữ liệu giúp giảm thiểu số lượng Request không cần thiết.
        \item \textit{Optimistic Updates} để cập nhật giao diện ngay lập tức trước khi nhận phản hồi từ Server, tạo cảm giác mượt mà cho người dùng.
        \item Tự động thực hiện truy vấn lại (Background Refetching) khi thiết bị kết nối mạng trở lại.
    \end{itemize}
    \item \textbf{Đảm bảo an toàn kiểu dữ liệu (Type-safety):} Toàn bộ các Endpoint được định nghĩa dưới dạng module hóa trong TypeScript, áp dụng Generic Types cho cả Request và Response, giúp hạn chế tối đa lỗi Runtime.
\end{itemize}

\subsubsection{Chiến lược quản lý trạng thái ứng dụng (State Management)}

Ứng dụng sở hữu cấu trúc dữ liệu phức tạp bao gồm quản lý nhóm, kho thực phẩm và lịch ăn uống. Tác giả đã áp dụng mô hình quản lý trạng thái phân tầng:

\begin{itemize}
    \item \textbf{Trạng thái phía Client (Zustand):} Sử dụng thư viện Zustand với ưu điểm nhẹ và hiệu suất cao hơn so với Redux. Các trạng thái về phiên đăng nhập (\textit{Auth State}), bộ lọc dữ liệu (\textit{Filters}) và tùy chỉnh người dùng được tổ chức thành các Slice riêng biệt.
    \item \textbf{Trạng thái phía Server (React Query):} Đóng vai trò là nguồn dữ liệu tin cậy (Single Source of Truth) cho các thông tin từ cơ sở dữ liệu.
    \item \textbf{Cơ chế duy trì trạng thái (Persistence):} Tích hợp Middleware \texttt{persist} của Zustand kết hợp với \texttt{AsyncStorage} để duy trì các trạng thái quan trọng ngay cả khi ứng dụng bị đóng hoặc khởi động lại thiết bị.
\end{itemize}

\subsubsection{Giải pháp lưu trữ dữ liệu cục bộ và bảo mật}

Để đáp ứng các yêu cầu khác nhau về bảo mật và hiệu suất, hệ thống lưu trữ phía Client được thiết kế theo mô hình hai tầng:

\begin{table}[ht]

\textbf{Standard Storage} & AsyncStorage & User Profile, Settings, Caches. \\ \hline

Giải pháp này đảm bảo tuân thủ các tiêu chuẩn bảo mật cho ứng dụng di động (như OWASP Mobile Top 10) bằng cách mã hóa các thông tin nhạy cảm ở cấp độ phần cứng (Keychain trên iOS và EncryptedSharedPreferences trên Android).

\subsubsection{Hệ thống đa ngôn ngữ và chuẩn hóa hiển thị}

Mặc dù mục tiêu hiện tại là thị trường Việt Nam, kiến trúc ứng dụng vẫn được thiết kế để sẵn sàng mở rộng đa ngôn ngữ (Internationalization) thông qua giải pháp \textit{Constants-based Mapping}:

\begin{itemize}
    \item \textbf{Ánh xạ Enum:} Chuyển đổi các giá trị Enum từ Backend (thường là tiếng Anh như \texttt{VEGETABLES}, \texttt{FRIDGE}) sang ngôn ngữ hiển thị tương ứng thông qua một lớp Utility tập trung.
    \item \textbf{Quản lý thông báo tập trung:} Toàn bộ các thông điệp lỗi và thông báo thành công được định nghĩa trong các hằng số, giúp đảm bảo tính nhất quán về thuật ngữ trên toàn bộ giao diện người dùng.
\end{itemize}

\subsubsection{Tích hợp dịch vụ nền tảng (Native Features)}

Thông qua Expo SDK, ứng dụng đã khai thác tối đa các tính năng đặc trưng của thiết bị di động để nâng cao trải nghiệm người dùng:

\begin{itemize}
    \item \textbf{Push Notifications:} Triển khai thông báo đẩy nhằm nhắc nhở người dùng về thực phẩm sắp hết hạn và lịch trình bữa ăn. Hệ thống hỗ trợ xử lý thông báo cả khi ứng dụng đang chạy nền hoặc đã đóng hoàn toàn.
    \item \textbf{Xử lý hình ảnh (Camera \& Image Picker):} Cho phép người dùng cập nhật ảnh thực phẩm và công thức nấu ăn. Hình ảnh trước khi tải lên được xử lý nén (Compression) và định lại kích cỡ (Resizing) để tiết kiệm băng thông và không gian lưu trữ của Server.
    \item \textbf{Tối ưu hóa hiển thị hình ảnh:} Sử dụng thư viện \texttt{expo-image} hỗ trợ các định dạng thế hệ mới như WebP và AVIF, kết hợp với cơ chế hiển thị \textit{Blurhash} giúp cải thiện tốc độ tải trang và chỉ số trải nghiệm người dùng (UX).
\end{itemize}
